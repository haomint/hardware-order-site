# 五金订货网站｜开发约束

> 适用于参与本项目的所有开发方。产品需求以根目录的 `hardware_order_prd_v1.md` 为准；本文档只规定「怎么协作、怎么写」。
>
> 日期：2026-11-12

## 1. 分工与目录

| 目录 | 负责方 | 内容 |
|---|---|---|
| `web/` | Claude | 前台商城与后台管理的全部页面 |
| `server/` | Codex | API、数据库、鉴权、通知、备份脚本 |
| `shared/` | 契约，双方只读 | 接口的请求/响应数据结构（TypeScript + zod） |
| `docs/` | 店主 | 开发约束、接口文档、部署说明 |
| 根目录 | 店主 | PRD、`CLAUDE.md`、`AGENTS.md` |

规则：

1. 只修改自己负责的目录。发现对方目录的问题，写明现象和复现方法提出来，不动手修。
2. `shared/` 的任何改动都必须先经店主同意。
3. 超出 PRD 的功能一律不做，先记录并询问店主。
4. PRD 与本文档冲突时，以 PRD 为准，并告知店主。

## 2. 接口契约

**唯一事实来源是 `shared/` 里的代码**，接口文档由它生成。

- `shared/` 用 TypeScript + zod 定义每个接口的请求体、响应体和枚举（订单状态、收款标记、配送方式等）。前端和后端都直接引用这些定义，不各自重写一份。
- 人读的接口文档放在 `docs/api/`，由 `shared/` 的定义自动生成（OpenAPI，可用 `@hono/zod-openapi` 之类的工具）。**不手工编辑生成的文档**；生成脚本由后端维护。
- **起草流程：** Codex 起草 → Claude 从前端使用角度审阅并提出修改 → 店主确认 → 双方开工。
- **变更流程：** 提出方说明改什么、为什么 → 店主同意 → 一方修改 `shared/` → 重新生成文档 → 另一方跟进。
- **按阶段定契约：** 阶段 A（分类、商品、登录、图片上传）的契约先定，阶段 B（下单、订单、收款标记、导出）和阶段 C（通知相关配置）在各阶段开始前定。
- **前端不等后端：** 契约确定后，前端用符合契约的假数据开发，后端完成后再对接。

## 3. 共同约定

| 事项 | 约定 |
|---|---|
| 金额 | 存储和传输一律用「分」的整数；只在页面显示时转为元 |
| 价格面议 | 商品的价格字段为 `null`，不用 0 表示 |
| 时间 | 接口传 ISO 8601 格式的 UTC 时间；页面按北京时间显示 |
| 错误格式 | `{ code, message }`；`code` 是稳定的英文标识，`message` 是可直接给用户看的中文 |
| HTTP 状态码 | 400 参数错误、401 未登录、404 不存在、409 冲突（如重复提交、商品已下架）、429 请求过频、500 服务端错误 |
| 接口路径 | 公开接口 `/api/...`，后台接口 `/api/admin/...` |
| 鉴权 | 后台使用 httpOnly Cookie 会话；前端不保存任何令牌 |
| 防重复提交 | 下单请求带一个由前端生成的幂等键，同一个键只生成一笔订单 |
| 图片 | 接口返回相对路径，压缩图和缩略图各一个字段 |
| 订单号 | 格式 `WJ-YYYYMMDD-NNNN`，由服务端生成 |
| 分页 | 列表接口统一用 `page`、`pageSize`，返回 `items` 和 `total` |
| 密钥与配置 | 只放环境变量；提供不含真实值的 `.env.example`；不进代码仓库 |
| 语言 | 界面文案、错误提示用简体中文；代码标识符用英文；注释中英均可 |

## 4. 前端约束（Claude）

**技术：**

- React + TypeScript + Vite，纯静态构建，不做服务端渲染。
- 样式用 Tailwind CSS；不引入大型组件库。
- 前台和后台在同一个项目，后台位于 `/admin` 路径并按需加载，客户不会下载后台代码。
- 购物车、熟客联系信息只存 localStorage，读写要容错（数据损坏或被清空时页面仍可用）。
- 前端的校验只为体验，不视为安全措施。

**适配：**

- 以 375px 手机宽度为设计基准，页面不得横向滚动；后台的订单相关页面同样手机优先。
- 必须兼容微信内置浏览器（安卓与 iOS）。
- 商品列表使用缩略图并懒加载。

**视觉方向（默认方案，店主可随时调整）：**

- 整体干净、朴素、可信，像一份清晰的产品目录，不做促销风格。
- 主色用沉稳的深蓝，仅「加入购物车」「提交订货单」等主要操作用醒目的橙色。
- 正文字号不小于 16px，按钮和可点击区域高度不小于 44px，照顾年纪较大的客户。
- 商品图片是主角：白底、留白充足、信息层级清楚（名称 → 型号 → 参考价）。
- 颜色、字号、间距统一定义为设计变量，之后调整风格只改一处。
- 前台完成首页和商品详情两个页面后，先给店主看效果，确认方向后再铺开其余页面。

## 5. 后端约束（Codex）

**技术：**

- Node.js LTS + Hono + SQLite，单进程运行。
- 目标服务器为 2 核 2G 且有其他项目共用，常驻内存应控制在 200MB 以内。
- 数据库结构变更一律走迁移脚本，不手工改表。
- 静态前端由 Nginx/Caddy 提供，后端只负责 `/api` 和上传图片的访问。

**业务规则（详见 PRD）：**

- 所有字段在服务端校验；预估金额由服务端按当前价格重算，不信任前端传入的价格。
- 订单保存下单时的商品快照（名称、型号、单位、单价）。
- 提交订单时重新检查商品状态，含已下架或缺货商品时返回 409 并指明是哪些商品。
- 订单写库成功后才发通知；通知失败不影响下单结果，失败要记录并可重试。
- 订单状态和收款标记是两个独立字段，各自记录修改时间。

**安全：**

- 密码用安全哈希（argon2 或 bcrypt）；禁止默认口令；登录接口限流。
- 下单接口按 IP 限流。
- 上传图片校验类型和大小，服务端重新编码后保存，不保留原始文件。
- 通知消息不包含完整手机号、地址或任何密钥。

**测试：** 下单、金额计算、状态流转、收款标记、鉴权、防重复提交必须有自动化测试。

## 6. 代码管理

- 一个 Git 仓库，包含 `web/`、`server/`、`shared/`、`docs/`。
- 小步提交；提交信息以 `web:`、`server:`、`shared:` 或 `docs:` 开头，说明改了哪一方。
- 不提交：`.env`、数据库文件、上传的图片、`node_modules`、构建产物。
- 提交前自己的部分必须能通过类型检查和已有测试。

## 7. 验收

- 按 PRD 的阶段 A → B → C 推进，每个阶段以 PRD 第 08 节的验收标准为准。
- 每个阶段结束时，前后端对接后在真实手机的微信里走一遍完整流程。
- 上线前逐条过 PRD 8.1 的发布前测试清单。
